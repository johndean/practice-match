# Account screens from the V3 gate components — design

**Date:** 2026-09-07 · **Status:** approved by John (design and the three rulings in conversation, 2026-09-07; the written spec, 2026-09-08: "approved") — executing as `docs/superpowers/plans/2026-09-08-account-screens.md` · **Wave:** 2a (identity), after Task I8a · **Supersedes:** the "Rev 3 design package" blocker recorded in `.worktrees/feat-identity/.superpowers/sdd/2026-09-05-practice-match-identity-access-email/task-I8-preflight.md`.

## 1. Why

The Wave 2a API implements the whole account lifecycle (sign up → verify → apply → decision → sign in; forgot/reset; staff invites; the applicant's answer and re-apply), but the approved V3 design has screens only for sign-in, the access-request form, two status cards (pending, declined) and Admin Users. Under the project rule that nothing is invented, the missing screens blocked I8b, I8c and the QA hand-back.

John's ruling (2026-09-07): **clear the blocker by composing the missing screens strictly from the existing V3 design's components and patterns, changing nothing in the existing design, so the rest of the site stays pixel for pixel.** The Admin → Permissions tab is **deferred** (a fifth tab would move the four Admin screens); the matrix stays reachable through the API and the table mapping Task I7 built.

## 2. The building blocks (all existing; nothing new is styled)

The gate screen (`showGate`) has a fixed frame: the band title, the left column (heading, two paragraphs, the three numbered points), the right column, the navy footer band. The right column renders exactly one card:

- **Form card** (`gateSignin`, `gateApply`): white card, band header (title 20 px uppercase + 13 px sub-line), 24/26 px body with labelled inputs (12 px steel label, 42–44 px input), the grey left-bordered error box, the 48 px blue uppercase primary button, a 14 px centred link line.
- **Status card** (`gateStatus`): white card, grey header (`status.headStyle`) with an 11 px kicker and a 22 px uppercase title, a 15 px body paragraph, key/value rows (`status.meta`), then two buttons — `status.primary` (blue, flexible) and the fixed secondary "Sign in" (`goSignin`).

Every new screen is a new value of `state.gate`, rendered by a new `<sc-if>` block appended in the right column **after** the existing `gateStatus` block, built only from those elements. Because the new blocks render nothing for the existing states, the 28 approved states keep their DOM and pixels; the amendment proof (`frontend/tests/design-amendments.test.ts`) and the pixel/DOM oracles pin that.

**The notice slot (refinement after self-review).** The status card's secondary button is the fixed "Sign in", so an outcome whose only next step is signing in would have shown two identical buttons. Those outcomes (3a, 4b, 5b, 6b and an expired invitation) therefore land on the **existing sign-in card** and speak through its existing message box — the grey, left-bordered block that today shows `form.errorText`. It is fed by a second state field (`formNotice`) through the same template slot, so the sign-in card's markup is untouched and the box appears only when a message exists.

**Re-apply needs no new screen.** A `declined` account lands on the existing declined card ("Access was not granted"); its existing primary "Reply with more information" opens the existing Request Access form pre-filled from `GET /api/applications/me → current.fields`; "Submit request" posts `POST /api/applications` (a new row, since the account is declined) and lands on the existing pending card. A `verified` account lands on the Request Access form directly (Task I8a's bootstrap).

## 4. The three touches to an existing screen — John's rulings

1. **Forgot-password entry (agreed).** The sign-in card's footer line becomes "Not approved yet? Request access · Forgot your password?" — the second link opens `forgot`. Only `gate-signin` moves, and Task I8a already re-baselines it (the "Email" label and the shortcut block's removal).
2. **Sign-in sub-line ("remove the VIN language").** "Use your VIN credentials." becomes "Use the email and password you registered with." — same round, same screen. The label "VIN username or email" → "Email" is already amendment A7.1. References to "VIN Foundation staff" are the organisation's name and stay.
3. **The status cards' secondary "Sign in" (agreed).** Label unchanged (no pixel moves); behaviour: when a user is signed in, `goSignin` signs them out through the adapter first, then shows the sign-in card. Same for the "Sign out" link on screen 7.

## 5. Wiring

- **Routes** (`frontend/src/router/routes.ts`, `sync.ts`): `/signup`, `/forgot`, `/verify`, `/reset`, `/accept-invite` render the single component like every other route; `routeToPatch` maps them to `{ screen: 'gate', gate: 'signup' | 'forgot' | 'verify' | 'reset' | 'invite' }`, capturing an incoming `?token=` into `state.gateToken`; `stateToRoute` maps those gate values back to the bare paths (the app never writes a token into a URL); all five are public (no `ROUTE_PERMS` entry, `gate` screen). The verify landing POSTs its token on arrival and replaces the history entry so the token leaves the address bar (spec S3); reset and invite hold the token in state until their form submits, then replace history the same way.
- **The prototype's script** (design amendments, family **A8**; Task I8a's adapter `this.props.auth` is the dependency): `gateSignup/gateCheckEmail/gateForgot/gateReset/gateInvite/gateAnswer` flags mirroring `gateSignin/gateApply`; `gateStatus` widened to every status value (`pending`, `rejected`, `check-email`, `verify-expired`, `reset-expired`, `unavailable`); `statusMap` gains the entries of §3 (their `headStyle` is the existing grey one); `form` gains the notice (`error: !!(s.formError || s.formNotice)`, `errorText: s.formError || s.formNotice`); form values and setters mirror `form`/`setEmail`/`setPw` (`signup`, `forgot`, `reset`, `invite`, `answer` sub-objects on state, all fields empty by default); each submit calls the adapter (`auth.signUp`, `auth.forgot`, `auth.verify`, `auth.reset`, `auth.acceptInvite`, `auth.answer`) when present and otherwise performs the prototype's fixture transition (so the reference keeps working with no adapter); `goSignin` and the new `goSignOut` route through `auth.signOut` when a user is signed in (§4.3). Bootstrap (A5.4) gains `unverified → check-email` and `needs_review → answer`.
- **The adapter** (`frontend/src/app.setup.js`, from Task I7's `api.ts`): `signUp(email, pw)`, `forgot(email)`, `verify(token)`, `reset(token, pw)`, `acceptInvite(token, pw)`, `answer(applicationId, text)`, `applicationsMe()`; all throw `AuthError(code, message)` and the cards show `message`. Password strength is enforced by the server (zxcvbn ≥ 3, HIBP) and its message is what the form shows; the client checks only that the two passwords match. (The spec's "checked client- and server-side" is met on the server; a client-side zxcvbn would cost the bundle budget — recorded as a default for John.)

## 6. Test oracle and fixtures

- **Approved states** (`frontend/tests/screens.ts`, both targets): `gate-signup`, `gate-check-email`, `gate-verify-expired`, `gate-forgot`, `gate-reset`, `gate-reset-expired`, `gate-invite`, `gate-answer`, `gate-unavailable`, `gate-reapply` (the existing apply form pre-filled from a declined application), and five sign-in-card-with-notice states: `gate-signin-verified`, `gate-signin-reset-sent`, `gate-signin-password-updated`, `gate-signin-invite-set`, `gate-signin-invite-expired`. The reference reaches each through the `startGate` switch (its enum grows to every gate value, plus a `startNotice` value for the five notice states; the reference's fixture transitions supply the outcomes). The app reaches each through real routes and real API calls.
- **Seeded fixtures** (`scripts/seed_persona.py`, test and QA only, refused on production — the existing rule): accounts `unverified@`, `verified@`, `pending@`, `needs-review@` (with an open application carrying `decision_note` "Which practice do you work at now, and in what role?"), `declined@` (with a declined application whose `fields` pre-fill the re-apply form), `invited@practice-match.test`; and single-use tokens with **documented test-only raw values** — twelve each of `verify` (for `unverified@`), `reset` (for `verified@`) and `invite` (for `invited@`) — recreated on every run (the Playwright `api` web server seeds before it serves). The harness takes the next unused token per capture (visual, DOM and smoke each consume one). A wrong token produces the expired cards against the real API. Sign-up and forgot are exercised live once per run with a throwaway address (limits: signup 5/h/IP, forgot 3/h/email); the screenshot states use the seeded accounts, never a live sign-up.
- **Gates**: every new behaviour has a characterisation test first (`frontend/src/logic.test.ts`, real `Component`, fake adapter object); `design-amendments.test.ts` proves pristine + amendments == the design and pins the A8 ids; `app-generated.test.ts` proves `logic.js`/`App.vue` are regenerated; the pixel and DOM oracles cover the new states at zero tolerance and prove the 28 existing states did not move (their baselines are unchanged by this work); `tests/test_docs.py` pins the seeded values against the harness; backend 100 % lines and branches unchanged.

## 8. Acceptance

A stranger on QA can sign up, receive the email, verify, sign in, land on Request Access, submit, see the pending card; staff can request information, the applicant answers and re-submits, is declined, re-applies; a staff invite link from `scripts/bootstrap_admin.py` opens the set-password card and the admin signs in; forgot/reset works end to end; a signed-in buyer visiting `/admin` sees the "not available" card — and every one of the 28 previously approved states is pixel- and DOM-identical to before this work.
