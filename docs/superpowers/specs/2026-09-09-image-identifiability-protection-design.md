## 0. The directive, and where this sub-project sits

John's directive is a production-grade de-identification system for the marketplace's image uploads with one seller control — "IDENTIFIABLE IMAGE CONTENT  [ SHOW ] [ NOT SHOW ]", default "NOT SHOW", "The safest privacy state is the default" (§1). It must cover "the ENTIRE image-upload lifecycle" and "EVERY image associated with the listing" with "NO path through which an image can bypass privacy processing" (§2), through a layered pipeline — validation, "OCR against EVERY image", identity matching against "all known listing identity information", a vision model "where available" that "MUST NOT replace OCR", and aggregation into "a structured detection result" (§4) — producing, under NOT SHOW, "a buyer-safe derivative" with "irreversible/opaque redaction rather than relying solely on Gaussian blur" (§5). Every image carries "an explicit privacy-processing state" with the error states `PROCESSING_FAILED`, `REDACTION_FAILED`, `REVIEW_REQUIRED`, `REPROCESS_REQUIRED` — "No image may silently fall through the state machine" (§6). The listing holds "a single authoritative setting: identifiable_content_visibility" (§7); "Selecting SHOW does NOT mean: skip scanning" (§8); under NOT SHOW "buyer MUST NOT receive the original" by any route and "The backend must enforce this. Do NOT rely solely on frontend hiding" (§9, §12). The seller gets "a SIMPLE review experience" — "✓ Looks good" or "+ Hide something", with the ability to "manually draw/select an additional redaction region" (§10) — and publishing is "blocked until" every image is processed and, under NOT SHOW, "seller explicitly confirms the result"; "Never allow AI_PASSED to mean READY_TO_PUBLISH" (§11). Originals are kept "private" and "NEVER overwrite[n]" (§13); every delivery path is audited (§14); toggle changes never delete derivatives (§16); a photograph added after publication "must NEVER temporarily appear to buyers in original form" (§17); an auditable record exists per image (§18); failures "fail CLOSED" (§19); the security audit (§20), the twenty-six test scenarios A–Z (§21) and the twenty-seven acceptance criteria (§22) each map to a concrete section below; and nothing anywhere claims perfect detection (§23). His process rule (§24): map the architecture first — "DO NOT begin coding until you have mapped the existing architecture" — which is §A and §B of this document.

**Placement (controller ruling 1).** This is its own sub-project — this spec, then `docs/superpowers/plans/2026-09-09-image-identifiability-protection.md` — executed in worktree `feat-image-identifiability` cut from `main` **after** two merges: (a) the seller lifecycle branch (Tasks SL7–SL9 of `2026-09-08-seller-listing-lifecycle.md`), which supplies the `listing_asset` table, `ObjectStore`, `app/media/encode.py`, the seller and admin routers, the wizard adapter and the publication routes this design hooks into — on `main` today none of those exist (§A.0); and (b) the A19 photo lightbox (`2026-09-09-photo-lightbox-and-arrows.md`), whose dialog is the seller's review viewer (§C.9). It lands **before** the map engines and before the roadmap's "Admin & seller controls" stage: the map engines change no image path, while every later seller-control screen must be built on a delivery layer that already refuses originals. The plan states both preconditions with the merge SHAs filled at dispatch. The release number is the controller's at hand-back, lockstep (`tests/test_versions.py`), never set here.

### C.1 The listing setting (D-IDP-14)

`listing.identifiable_content_visibility text NOT NULL DEFAULT 'NOT_SHOW' CHECK (identifiable_content_visibility IN ('SHOW','NOT_SHOW'))` — migration `040` (§D). 5. on a `published`/`paused` listing the existing D3 arm (`EDIT_REENTERS_REVIEW`, `:105`) still moves it to `in_review` — a flip is an edit buyers must not see until re-published — so §16's "block publication" is structural and the gate in §C.8 decides the re-publish.

| any | (row gone) | `DELETE …/assets/{asset_id}` — the three objects and the row | owner |

**Staleness is a flag, not a state (D-IDP-16; skeptic findings 1 and 2).** The first draft sent a row whose scan had gone stale to `REPROCESS_REQUIRED` and promised its derivative would "stay served" — which `lap_visible_ready_ck` forbids and the resolver refuses, so a `PROCESSING_VERSION` bump would have blanked every photograph on every published listing (or crashed the sweeper on the CHECK). Instead `reprocess_reason` (`VERSION` \| `IDENTITY_CHANGED` \| `OPERATOR`, §C.3) is set on a ready row **without changing its state**, and the in-place re-run (§C.5) consumes it while the current derivative goes on being served. Two things set it: the sweeper, when `processing_version < PROCESSING_VERSION`; and the seller's step-1/step-2 PATCH of `name`, `city` or `zip` (`STEP_FIELDS[1]`/`[2]`, `:115-122` — sellers have no field for `street` or `phone`), which marks every ready row of the listing in its own transaction and enqueues after the commit (that PATCH already re-enters review on a published/paused listing under D3, so the re-run completes before any republish — the gate's `STALE`, §C.8). The reviewer's first-publish `state`/`market` (`admin_listings.py:229-250`) marks NOTHING: they are written in the SAME `UPDATE` that sets `status = 'published'`, so a mark before it would make migration 042's trigger refuse every first publish of a listing with photographs, and a mark after it would leave a published listing with every photograph non-ready — the primary flow unpublishable or dark. The matcher reads `state` and `market` when present (every post-publication re-run has them) and the gap is recorded as a limitation: a two-letter state code alone identifies nothing narrower than a state, and the city token already carries the locality.

**The confirmation-reset rule (skeptic finding 6).** Every write that produces, or will produce, a derivative the seller has not seen clears `seller_confirmed`, `seller_confirmed_at`, `seller_confirmation_account_id`, `final_privacy_state` and `confirmed_sha256`, sets `seller_review_status := 'pending'` and `buyer_visible := false` (under SHOW `buyer_visible` returns to true with readiness): the claim of a fresh run (a retry, Try again, a lost-task recovery, the flip's re-enqueue), a mask add or remove, the SHOW → NOT_SHOW flip for a row not confirmed under NOT_SHOW, the third failed in-place re-run. The ONE derivative write that does not reset is the in-place re-run of a confirmed row (§C.5), whose region set is by construction a superset of the confirmed one; it advances `confirmed_sha256` with `redacted_sha256` in the same `UPDATE`. `lap_confirmed_ck` (`confirmed_sha256 = redacted_sha256` whenever `seller_confirmed`) makes "confirmed" and "confirmed against a derivative other than the one served" mutually exclusive at the database, so "confirmed against its current derivative" (§C.1 step 3) is a column comparison, not an inference.

Invariants the CHECKs and tests hold: no state is skipped silently; an error state is never left by anything but the claim of a retry, a Try-again or a delete; `buyer_visible` is never true outside the three ready states; a confirmed row's `confirmed_sha256` always equals its `redacted_sha256`; `REPROCESS_REQUIRED` is reached from `PROCESSING` alone; nothing ever writes `redacted_storage_key := original_storage_key`.

### C.5 The pipeline, stage by stage (D-IDP-6)

Module layout (controller ruling 5): `app/tasks/media.py` (the Celery tasks), `app/privacy/__init__.py` (`PROCESSING_VERSION`), `app/privacy/identity.py` (matching), `app/privacy/vision.py` (the Anthropic adapter), `app/privacy/aggregate.py` (region union and expansion), `app/media/redact.py` (the fill and re-encode; extends `encode.py`'s primitives, never duplicates them), `app/privacy/delivery.py` (the resolver, §C.7), `app/privacy/ocr.py` and `app/privacy/barcodes.py` (thin typed adapters over the engines — the only modules that import them). The api never imports the engines; the worker never serves bytes.

**Step 0 — the upload route (api, synchronous).** Unchanged refusals (415, 413, 422 `BAD_IMAGE`, 503, 404, 409) plus: magic-byte sniff for the three photo types (`\xff\xd8\xff`, `\x89PNG\r\n\x1a\n`, `RIFF….WEBP`) mirroring `_sniffed` for documents (`:698-712`) → 422 `BAD_IMAGE` when the bytes disagree with the header (closes the skeptic's decode-anything finding); `encode_webp` runs under `anyio.to_thread.run_sync` (anyio is a main dependency, `passwords.py` precedent) so the loop is not blocked; the route keeps `_insert_asset`'s documented order (`:810-828`: the row is inserted inside the open transaction and the object is written before the commit, so a committed row can never point at an object that was never written) — it inserts the asset row and the privacy row (`UPLOADED`, `processing_version = PROCESSING_VERSION`), puts `original.*` after an `exists()` check and then `display.webp`, appends to `listing.photos`, commits, then enqueues `media.process_photo(asset_id, version)` — **after** the commit, so a task can never find no row; the enqueue failing leaves an `UPLOADED` row for the sweeper. The asset uuid is minted per request, so `exists()` can only be true for a key some earlier, rolled-back request wrote — the 409 `STORAGE_CONFLICT` is defence in depth, reached in tests by planting an object at a patched uuid, never by a seller's action (skeptic finding 25). A put that fails after `original.*` was written rolls the row back and leaves that object with no row: unreadable (every read goes through a row), at most 15 MiB, and the ONE orphan this design knowingly leaves — recorded here; a prefix-versus-rows reconciliation is an operator script for later, not built now. The synchronous 422 stays because the wizard's single error slot (`wizErr`) is how a seller learns a file is not a photograph.

**Step 1 — validate (worker).** Fetch `display.webp` (and, once, `original.*` for the barcode pass); Pillow decode with the same `MAX_IMAGE_PIXELS` bound; record width/height in `ocr` (`"size": [w, h]`); any decode error → `PROCESSING_FAILED` (`last_error = 'UNDECODABLE'`).

**Step 2 — OCR (worker; `rapidocr-onnxruntime` 1.4.4 + `onnxruntime`, D-IDP-1a).** `RapidOCR()(img)` → `[[quad], text, score]` per line, rotated quads, recorded in `ocr.lines`; a second pass on a 2× upscale for lines shorter than 24 px (directories, business cards); the engine object is built once per prefork child (module-level lazy singleton) with `intra_op_num_threads = 1`. Import or inference error → `PROCESSING_FAILED` (`OCR_UNAVAILABLE`/`OCR_ERROR`) — OCR is never skipped (§4 "OCR against EVERY image"). Regex classes run over every line and over the joined text: NANP phone, URL/domain (a maintained TLD list), email, street address (`\d+\s+\w+\s+(St|Ave|Rd|Blvd|Dr|Ln|Pkwy|Hwy|Suite|Ste)\b`, case-insensitive), social handle (`@\w{3,}`), five-digit ZIP — each hit is an identifying region regardless of matching.

**Step 2b — barcodes (`zxing-cpp`, D-IDP-1c).** `read_barcodes(img, try_rotate=True, try_downscale=True)` on display and on the original (a fill cannot be hidden under an OCR region), each result's four corners a polygon expanded 15 % about its centroid; **every 2D symbol is a redaction region under NOT_SHOW regardless of payload** (a QR cannot be reviewed by eye and the worker never fetches a URL — no egress, no SSRF); the payload is classified offline (`url`, `phone`, `vcard`, `text`) and run through the matcher for the record; an undecodable finder pattern (`return_errors=True`) is still a region. Recorded as **(Q) D-IDP-7**: this exceeds §3's "where they resolve to identifying information" toward hiding; the seller can Remove an unnecessary mask.

**Step 3 — identity matching (`app/privacy/identity.py`, stdlib only).** Inputs read from the listing row at run time: `name`, `street`, `city`, `state`, `zip`, `phone`, `slug`, the seller's own text fields as alternates (`facility`, `services`, `hours` contribute tokens, never whole-string matches), the owning account's email **domain** (`account.email`, the part after `@`; never the local part), and abbreviations derived from the name — the initials of every word and of every word minus the generic set (`animal, hospital, veterinary, vet, clinic, pet, care, center, centre, of, the, and, for, dvm`). Normalisation: casefold; strip punctuation to spaces; collapse whitespace; an OCR-substitution map applied to BOTH sides (`0↔o`, `1↔l↔i`, `5↔s`, `8↔b`, `2↔z`, `rn↔m`, `vv↔w`). Methods, in order, each recorded with its score: exact; substring (a line contains a field or a field contains the line, min 4 chars); token-set overlap ≥ 0.6 for lines of ≥ 2 tokens; `difflib.SequenceMatcher(None, a, b).ratio() ≥ 0.85`; **distinctive-token**: any name token of ≥ 5 chars outside the generic set appearing in a line (so "Hill Country" on a sign matches "Hill Country Animal Hospital"); abbreviation exact on lines of 2–6 upper-case letters. No new dependency (controller ruling 5: `difflib`). Columns for website/email/social handle do not exist on `listing` (audit) — recorded; the regex classes cover them in the image.

**Step 4 — vision (`app/privacy/vision.py`, D-IDP-1b, (Q)).** Adapter around the Anthropic Messages API, Python SDK `anthropic` 1.x (built on `httpx2`, distinct from the project's `httpx` — no name conflict; `poetry lock` must be run and its result quoted). Client: `anthropic.Anthropic(api_key=settings.anthropic_api_key, max_retries=2, timeout=60.0)` — **the key is passed explicitly from `Settings`** (a new `anthropic_api_key: str | None = None`, read from settings not `os.environ`, so `monkeypatch.setattr(settings, …)` is the test seam — the in-tree precedent is split and this spec picks the Resend/`require_archive` side), so an unset Railway variable can never be satisfied by `ANTHROPIC_AUTH_TOKEN`, an `ant auth` profile or WIF. Request — ONE call form, on the beta namespace, because `fallbacks` and `betas` are accepted only by `client.beta.messages.*` and the non-beta `client.messages.parse(...)` cannot carry them (skeptic finding 9; the claude-api skill documents no beta `parse`, and SDK usage is never guessed): `client.beta.messages.create(model=VISION_MODEL, max_tokens=2048, betas=["server-side-fallback-2026-07-01"], fallbacks="default", output_config={"effort": "low", "format": {"type": "json_schema", "schema": VISION_SCHEMA}}, messages=[…])`, then `VisionResult.model_validate_json(<the first text block>)` — a Pydantic model (pydantic is already a main dependency through `pydantic-settings`) — as the schema check: `output_config.format` constrains the output, the validation is what the record trusts, and a `ValidationError` is the schema-failure outcome below. `VISION_MODEL = "claude-opus-5"` (a module constant; John may name another — one line); `thinking` omitted (adaptive by default on Opus 5 — the skeptic's cost correction: thinking tokens are output tokens, hence `effort: low`); `fallbacks: "default"` with its `server-side-fallback-2026-07-01` beta is the skill's standing instruction for `claude-opus-5` code, and a `fallback` content block in the response is recorded as `vision.model` (the model that actually answered). The image goes as `{"type": "image", "source": {"type": "base64", "media_type": "image/webp", "data": …}}` — `display.webp` bytes, ≤ 1600 px, under the high-resolution tier's 2576 px ceiling, so the API performs no resize and the returned boxes are in display pixels. The plan's first vision step probes the pinned SDK (`poetry run python -c "import anthropic, inspect; …"`) and quotes that `client.beta.messages.create` accepts `output_config`, `fallbacks` and `betas` before a line of adapter code is written. Prompt data: the practice name, city and state — never phone or street (data minimisation). Schema: `{"identifies_practice": bool, "regions": [{"kind": "logo|signage|uniform|vehicle|wall_graphic|document|business_card|directory|text|other", "label": str, "box": [x0,y0,x1,y1] in sent-image pixels, "confidence": "low|medium|high"}]}`. Outcomes: `settings.anthropic_api_key is None` → `vision.status = 'unavailable'`, `last_error` untouched, **the pipeline continues** (directive §4 "where available"; controller ruling 5) — the seller's review carries the rest and the record says so; key present and `RateLimitError`/`APIStatusError ≥ 500`/`APIConnectionError` after the SDK's retries, `stop_reason == "refusal"` (checked before reading `content`; `stop_details.category` recorded), `max_tokens`, or a body failing the schema → `vision.status = 'failed'` → `PROCESSING_FAILED` (`VISION_FAILED`/`VISION_REFUSED`) → retries → `REVIEW_REQUIRED`. **Unavailable is not a failure; a failure is never treated as unavailable.** Logged: `response._request_id` and exception class only — never the image, never the response text. A vision "no identifiers" never short-circuits OCR/regex/barcode regions or the seller confirmation (§11). `identifies_practice` true with no usable box → `vision.unlocalised = true`, the photograph still reaches `READY_FOR_REVIEW` (the seller's manual mask is the tool) — **(Q) D-IDP-8** whether John wants a per-photograph hint beyond the once-only copy. Cost, an estimate to be measured from `response.usage`: a 1600×1200 image is 58×43 = 2,494 visual tokens (⌈w/28⌉×⌈h/28⌉); with ~1,200 prompt tokens and ~800 output tokens including low-effort thinking, ≈ $0.04 per image at Opus 5's $5/$25 per MTok; a 50-photograph listing ≈ $2; `claude-sonnet-5` at $2/$10 is the cost lever John may choose, never the default.

**Step 5 — aggregation (`app/privacy/aggregate.py`).** Union of: OCR lines with an identity match, regex hits (their whole line), barcode polygons, vision boxes (every confidence — fail toward hiding; the seller removes what is unnecessary). Expansion: OCR/regex/barcode regions pad `max(12 px, 25 % of the shorter side)`; vision boxes pad `max(24 px, 20 % per side)` because "coordinate and localization outputs are approximate"; whole OCR line, never per word. Merge: regions whose expanded axis-aligned boxes overlap or sit within 8 px become one polygon (a sign is one block, not a picket fence that leaks letter count). Output: `redaction_regions` entries with `source: 'auto'`; `detected_regions` keeps the pre-expansion set. Deterministic: same inputs, same output (a property test).

**Step 6 — redaction (`app/media/redact.py`).** `Image.open(display).convert("RGB")` → `ImageDraw.Draw(img).polygon(points, fill=FILL)` for every region not `removed-by-seller`, plus rectangles for seller-drawn masks → `encode_webp(bytes)` (same ladder, same dimensions in and out since ≤ 1600 px never triggers `_within`, no metadata by construction) → `sha256`. `FILL = (0, 58, 112)` — the design's navy `#003a70` (`var(--color-navy)`, the done card's colour) — **(Q) D-IDP-9**, black is the alternative. Never blur, pixelate or mosaic: a constant fill carries no information about the covered pixels, so the lossy encoder receives none. `encode_webp` → `None` → `REDACTION_FAILED` (`ENCODE_TOO_LARGE`), fail closed. The derivative's size must equal display's (asserted); every pixel inside every region equals `FILL` (asserted per pixel in tests); no EXIF/ICC/XMP chunk (asserted).

**Step 7 — completion.** `redacted_storage_key`/`redacted_sha256` written → `REDACTION_GENERATED` → `READY_FOR_REVIEW`, `detection_at = now()`, `processing_version` stamped; under SHOW `buyer_visible := true`; the list cache dropped (a SHOW listing on the market shows the photograph the moment it is ready). A fresh run — from `UPLOADED`, a retry, Try again, a recovered lost task — arrives here with the confirmation columns at their defaults, because the reset rule (§C.4) was applied at the claim: a derivative the seller has not seen can never inherit `seller_confirmed`. The seller is not emailed (no new template without John's copy approval — A-SL19 Info-1 precedent); the step-6 pill is the signal.

**Retries, idempotency, versions, the sweeper (skeptic finding 4).** `media.process_photo(asset_id: str, version: int)` is registered by the call form (`celery_app.task(name="media.process_photo", acks_late=True, reject_on_worker_lost=True, time_limit=300, soft_time_limit=240)(process_photo)`, the census/mail shape — a plain function, no `bind=True`, no `self`) and **never raises** — the `_NotReady`/`_refuse` shape (`census.py:62-66`, `:118-124`): every outcome is a state write plus a returned summary. Retry is therefore not `Task.retry()` (which raises `celery.exceptions.Retry` and needs a bound task): a retryable failure writes `PROCESSING_FAILED`/`REDACTION_FAILED` with `last_error` and, while `attempts < 3`, re-enqueues itself with `process_photo_task.apply_async(args=(asset_id, version), countdown=BACKOFF[attempts - 1])`, `BACKOFF = (30, 120, 600)` seconds, then returns; the third failure writes `REVIEW_REQUIRED` in the same transaction. `acks_late` acks the message on return, so a retry is always a fresh message; `reject_on_worker_lost` redelivers the message of a child killed mid-run — the redelivered run finds the row `PROCESSING` with a recent `updated_at`, returns `in_progress` and writes nothing, and the sweeper's lost-task rule finishes the job; a hard `time_limit` kill acks the message, so the same rule covers it; `SoftTimeLimitExceeded` is caught as a failure (`TIMEOUT`) on the retry path. **The claim** is one statement — `UPDATE listing_asset_privacy SET processing_status = 'PROCESSING', attempts = attempts + 1, <the reset rule's columns>, updated_at = now() WHERE asset_id = %s AND (processing_status IN ('UPLOADED','PROCESSING_FAILED','REDACTION_FAILED','REPROCESS_REQUIRED') OR (processing_status = 'PROCESSING' AND updated_at < now() - interval '6 minutes')) RETURNING …` — and a run that claims nothing returns `already_processed`/`in_progress` and writes nothing, which is what makes a duplicate message harmless and what stops a late retry from clobbering a confirmation: a ready row is never claimed by this path. A run refuses `version < PROCESSING_VERSION` (a stale enqueue) the same way. A ready row is re-run only IN PLACE, through the stale flag (below). `media.sweep` runs on beat every 5 minutes and applies six rules, each one `UPDATE` or one enqueue: (1) `UPLOADED` older than 2 min → enqueue (the api's enqueue was lost); (2) `PROCESSING` older than 6 min (the hard limit plus a minute) → `REPROCESS_REQUIRED`, `last_error = 'TASK_LOST'`, enqueue; (3) `PROCESSING_FAILED`/`REDACTION_FAILED` with `attempts < 3` older than 12 min (the longest backoff plus two) → enqueue (a re-enqueue was lost, or a mask route's regeneration failed — that route sets the state and enqueues nothing itself); (4) `REPROCESS_REQUIRED` older than 6 min → enqueue; (5) a ready row with `processing_version < PROCESSING_VERSION` and no flag → `reprocess_reason := 'VERSION'`, `reprocess_requested_at := now()`, enqueue; (6) a flagged ready row older than 6 min → enqueue. `scripts/reprocess_photos.py [--listing ID | --all-stale]` sets `reprocess_reason := 'OPERATOR'` and enqueues (run in the worker container; joins `quality.yml:63`'s strict-mypy list). SHOW listings run the identical pipeline so switching to NOT_SHOW is instant when the derivative is valid (§16).

**The in-place re-run (D-IDP-16 — what a version bump does to a published listing; skeptic finding 1).** A ready row (`READY_FOR_REVIEW`, `SELLER_CONFIRMED`, `PUBLISHED`) carrying `reprocess_reason` is re-run without leaving its state: steps 1–5 run fresh; the seller's `manual` and `removed-by-seller` regions carry forward by id; the auto set is **replaced** on an unconfirmed row and **unioned** (`old ∪ new`, never fewer) on a confirmed one, and a new auto region whose box lies inside a `removed-by-seller` region's box is recorded in `detected_regions` and not filled; the fill runs; if the new sha equals `redacted_sha256` nothing is put; otherwise `redacted.webp` is overwritten and ONE `UPDATE` writes `redacted_sha256`, `confirmed_sha256 := redacted_sha256` where `seller_confirmed` (the union is what makes that honest: the new derivative hides a superset of what the seller confirmed, so nothing they never saw is revealed), `processing_version`, `reprocessed_at = now()`, `reprocess_reason := NULL`, `reprocess_requested_at := NULL`, `attempts := 0`, and the list cache is dropped (`?v=` changes). Until that `UPDATE` the OLD derivative is served under its old hash — a stale redaction is still a redaction and is never the original — and the state, `buyer_visible` and `lap_visible_ready_ck` are untouched, so a `PROCESSING_VERSION` bump darkens no listing. A failed in-place run counts an attempt and re-enqueues with the same backoff; the third failure moves the row to `REVIEW_REQUIRED` with the reset rule applied — a fail-closed null slot on a published listing, the pill reads Failed, and Try again is the seller's route back (through review, since `confirm` re-enters review on a published listing, A-SL15). A flagged row is an offender at the gate (`STALE`, §C.8): a NEW publish or republish waits for the re-run; an existing publication is untouched.

**Engines, sizes, licences (D-IDP-1, from the infra audit; every byte figure is an estimate until measured with `docker images`, the Pillow precedent — f454fe7 measured +42 MB against a ~10 MB estimate).** OCR: `rapidocr-onnxruntime` 1.4.4 (Apache-2.0, py < 3.13 fits `requires-python >=3.12,<3.13`, models bundled in the 14.9 MB wheel — offline, proven by a network-blocked test; requires the full `opencv-python`, hence apt `libgl1 libglib2.0-0` in the runtime stage beside `ca-certificates curl` — **(Q) D-IDP-10**: the alternative is vendoring the PP-OCR ONNX models and driving `onnxruntime` with Pillow/numpy preprocessing, dropping OpenCV) + `onnxruntime` ≥ 1.29 (MIT) — estimate +120–150 MB on the 634 MB BRANCH image; Tesseract (Debian `tesseract-ocr` 5.3.0, Apache-2.0, ~+50–70 MB with its pango/cairo/icu pull-in) is the recorded second choice with weaker scene-text recall; EasyOCR (torch, ≥ +700 MB) and cloud OCR (a third vendor receiving the un-redacted photograph) are rejected. Barcodes: `zxing-cpp` 3.1.1 (Apache-2.0, pure wheel ≈ 1 MB, no requires_dist). Vision: the Anthropic API as above; egress worker → `api.anthropic.com` recorded in DEPLOY.md. All three behind adapters with stub transports in tests (no model download, no binary, no network under `-W error`; the Anthropic seam is the adapter interface itself — a v1 `httpx.MockTransport` cannot be handed to the `httpx2`-based SDK). Worker sizing is a deployment prerequisite (§E).


### C.8 The publishing gate (D-IDP-12)

`app/privacy/gate.py::photos_not_ready(conn, listing_id) -> list[tuple[asset_id | path, status]]` — one SQL predicate used by every publication route, offenders returned for the envelope:

```
NOT_SHOW: every photo entry of listing.photos must have a privacy row with processing_status IN ('SELLER_CONFIRMED','PUBLISHED')
          and redacted_storage_key IS NOT NULL; a seed path entry is an offender ('SEED_UNPROCESSED')
SHOW:     every photo entry must have a privacy row with processing_status IN ('READY_FOR_REVIEW','SELLER_CONFIRMED','PUBLISHED');
          seed path entries pass
either:   any row in PROCESSING_FAILED / REDACTION_FAILED / REVIEW_REQUIRED / REPROCESS_REQUIRED / UPLOADED / PROCESSING is an offender
stale:    any row with reprocess_reason IS NOT NULL is an offender ('STALE') — its in-place re-run is pending (§C.5);
          a NEW publication waits for it, an existing publication is untouched
```

Under SHOW the floor is `READY_FOR_REVIEW`, not `SCANNED` — §11 (1) says "completed processing" and `SCANNED` is mid-run; this narrows the controller's ruling-8 range to what the directive states. Applied by: `submit_listing` (`:1181-1219`, after `_complete_enough`), `decide_listing` publish branch (`admin_listings.py:229` before the UPDATE), `set_status` republish (`:1222-1256`) — each refusing `422 PHOTOS_NOT_READY` with the envelope `{"error": {"code": "PHOTOS_NOT_READY", "message": "<§H string>", "photos": [{"id", "status"}]}}` (an additive key inside A5's `error`; pinned by test). The **backstop** is migration `042`'s trigger: `BEFORE INSERT OR UPDATE OF status ON listing` — `status` alone, matching §D's DDL (skeptic finding 16) — when `NEW.status = 'published'` and (`TG_OP = 'INSERT'` or `OLD.status <> 'published'`), evaluating the same predicate in SQL and raising `P0001 'PHOTOS_NOT_READY'` — a direct SQL publish (the `_publish` test helper, a future route, a hand-run UPDATE) cannot bypass it; the seeder's rows carry no asset rows and are SHOW, so they pass. On a successful publish the same transaction sets `PUBLISHED` on every photo row that was `SELLER_CONFIRMED` (or `READY_FOR_REVIEW` under SHOW); `PUBLISHED` means published at least once and is not reverted by a pause, unpublish or withdrawal (§C.4). The one way a published listing comes to hold a non-ready photograph is the third failed in-place re-run (§C.5), which leaves that slot null to buyers — never the original, never display. Per-asset `buyer_visible` (§C.3) is what the buyer surfaces filter on, so a photograph added after publication is a null slot to buyers from the moment it exists (§17) — **and** A-SL15 stands unchanged: the upload still moves a published/paused listing to `in_review`, and the reviewer's republish is refused until the new photograph is confirmed. `AI_PASSED` has no column and no code path: nothing reads `vision.identifies_practice == false` as readiness.

**`migrations/042_listing_publish_photos_ready_trigger.sql`**

```sql
-- The fail-closed backstop for directive §11: a listing cannot become `published` — by any route, by a
-- test helper, by hand — while a photograph is not ready. The routes evaluate the same predicate first
-- and answer 422 PHOTOS_NOT_READY with the offenders; this refuses whatever they missed.
CREATE OR REPLACE FUNCTION listing_photos_not_ready(l_id uuid, visibility text, photos jsonb)
RETURNS TABLE (entry text, status text) LANGUAGE sql STABLE AS $$
  WITH entries AS (SELECT e FROM jsonb_array_elements_text(photos) AS t(e) WHERE e IS NOT NULL)
  SELECT e, 'SEED_UNPROCESSED' FROM entries WHERE position('/' IN e) > 0 AND visibility = 'NOT_SHOW'
  UNION ALL
  SELECT e, coalesce(p.processing_status, 'NO_PRIVACY_ROW')
    FROM entries LEFT JOIN listing_asset_privacy p ON p.asset_id::text = e AND p.listing_id = l_id
   WHERE position('/' IN e) = 0
     AND (p.asset_id IS NULL
          OR (visibility = 'NOT_SHOW' AND (p.processing_status NOT IN ('SELLER_CONFIRMED','PUBLISHED')
                                           OR p.redacted_storage_key IS NULL))
          OR (visibility = 'SHOW' AND p.processing_status NOT IN ('READY_FOR_REVIEW','SELLER_CONFIRMED','PUBLISHED')))
  UNION ALL
  SELECT e, 'STALE'
    FROM entries JOIN listing_asset_privacy p ON p.asset_id::text = e AND p.listing_id = l_id
   WHERE p.reprocess_reason IS NOT NULL
$$;

CREATE OR REPLACE FUNCTION listing_publish_requires_ready_photos() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.status = 'published' AND (TG_OP = 'INSERT' OR OLD.status <> 'published') THEN
    IF EXISTS (SELECT 1 FROM listing_photos_not_ready(NEW.id, NEW.identifiable_content_visibility, NEW.photos)) THEN
      RAISE EXCEPTION 'PHOTOS_NOT_READY' USING ERRCODE = 'P0001';
    END IF;
  END IF;
  RETURN NEW;
END $$;

CREATE TRIGGER listing_publish_photos_ready BEFORE INSERT OR UPDATE OF status
  ON listing FOR EACH ROW EXECUTE FUNCTION listing_publish_requires_ready_photos();
```

The trigger fires on `status` alone (skeptic finding 16 — the first draft's DDL also named `photos` and `identifiable_content_visibility`, which the `OLD.status <> 'published'` guard made inert: a published row gaining a photograph leaves `published` in the same transaction under A-SL15, and a flip on a published row re-enters review under D3, so neither write can ever MAKE a row published, and the prose already said `OF status`). `tests/api/test_listing_assets.py:132-138`'s `_publish` helper gains the privacy rows it needs where a test plants photographs; a schema test proves a bare `UPDATE listing SET status='published'` with an `UPLOADED` photo raises `P0001`, and another that a flagged (`reprocess_reason = 'VERSION'`) row does the same.

## E. The processing pipeline in sequence, and the worker wiring

**Sequence (one photograph, NOT_SHOW listing, first upload).** 1 · The seller presses "Add files"; the browser POSTs the file; the api sniffs, bounds, decodes and encodes in a thread, puts `original.jpg` (guarded) and `display.webp`, inserts the `listing_asset` row and the `listing_asset_privacy` row (`UPLOADED`, version 1), appends the uuid to `listing.photos`, commits, then publishes `media.process_photo(asset_id, 1)` to the `media` queue and answers 201; the step-6 tile appears with the "Processing…" pill and no thumbnail. 2 · A prefork child on the worker takes the task (`acks_late`), sets `PROCESSING` (`attempts = 1`), fetches `display.webp` and `original.jpg`, validates, runs RapidOCR, the regex classes and zxing-cpp, reads the listing's identity fields, matches, calls the vision adapter (or records `unavailable`), writes `ocr`/`identity_matches`/`vision`/`detected_regions` and sets `SCANNED`. 3 · Aggregation produces `redaction_regions`; `redact.py` fills and re-encodes; the child puts `redacted.webp`, writes the key and sha, sets `REDACTION_GENERATED`, then `READY_FOR_REVIEW` with `detection_at`; `buyer_visible` stays false (NOT_SHOW);
